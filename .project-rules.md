# POS Frontend Project Guidelines & Architectural Rules

Always adhere to these architectural and performance rules when writing, optimizing, creating or editing code for this POS project.

---

## 1. Core Architectural Pattern
We use a **Hybrid Next.js App Router Architecture**:
1. **Server Components (`page.tsx`)**: Handle metadata, security, and pre-fetching of initial data collections (e.g. lists, select box configurations, or specific entities).
2. **Client Components (`*Client.tsx`)**: Marked with `"use client"`. Handle state, interactive UI (search, tab filters, dialogs/modals), optimistic updates, and toast notifications.
3. **Server Actions (`lib/api/*.ts`)**: Functions marked with `"use server"` that perform direct data mutations (GET, POST, PUT, DELETE) to the backend.

---

## 2. Rules for Data Fetching & Mutations

### No Manual API Proxy Routes & Mandatory requestApi Helper
- **DO NOT** create manually defined API routes (e.g., `app/api/foo/route.ts`).
- **DO NOT** use `fetch('/api/foo')` in client components or API modules directly.
- **ALL API calls** MUST be executed using the `requestApi()` helper function defined in `lib/api/client.ts`.
- Server Actions defined in `lib/api/*.ts` wrap `requestApi()` calls and are used directly inside components.

### Server-Side Data Pre-fetching
- All listing index pages, details/view pages, and add/edit forms **must** load their initial data collections on the server-side.
- If multiple lists or items are needed (e.g. categories, brands, and units lists for a product form), fetch them in parallel on the server using `Promise.all()` to prevent network waterfalls:
  ```typescript
  // In app/admin/foo/page.tsx
  const [dataRes, metadataRes] = await Promise.all([
    getData(),
    getMetadata()
  ]);
  ```
- If a details or edit payload fetch fails, instantly return Next.js `notFound()`.

### Client State Synchronization & router.refresh()
- When creating, editing, or deleting data in client components:
  1. Call the corresponding Server Action.
  2. On success, show a success toast notification.
  3. Call `router.refresh()` from `next/navigation` to trigger Next.js to re-fetch the server component's data.
  4. Use a `useEffect` hook inside the client component to sync local state with props when the server updates them:
     ```typescript
     // Inside Client Component
     useEffect(() => {
       setLocalData(initialDataProp);
     }, [initialDataProp]);
     ```
- For status toggles (e.g., switching Active/Inactive status), always use **Optimistic UI Updates**:
  1. Immediately toggle the local state in the UI.
  2. Fire the server action.
  3. If the server action fails, catch the error and revert the state back to its original value, displaying an error toast.

## 3. Performance & Rendering Optimization

### useMemo and useCallback
- Always wrap search filters, sorting logic, and complex calculations in `useMemo` to avoid expensive recalculations on every re-render.
- Wrap event handlers and callbacks that are passed to child components in `useCallback` to prevent unnecessary component re-renders.

### Internal Navigation
- Prefer Next.js `<Link>` component for routing. **STRICTLY PROHIBITED**: Do not use `window.location.href = ...` or `window.location.reload()`.
- Use Next.js `useRouter` hook (`router.refresh()`, `router.push()`) from `next/navigation` for programmatically redirecting and refreshing pages without loading a fresh document.

### Asset Optimization & Image Components
- **MUST** use the Next.js `<Image>` component (`next/image`) for all layout-stable images to prevent Cumulative Layout Shifts (CLS) and enable automatic WebP/AVIF optimization.
- Avoid raw `<img>` tags. If a raw `<img>` tag is unavoidable, always provide explicit `width` and `height` properties or placeholders.

---

## 4. State Management Best Practices

### Derived State vs Duplicate State
- **DO NOT** declare state variables for data that can be derived from existing state or props.
- For example, instead of declaring a state for `const [filteredList, setFilteredList] = useState([])`, compute it dynamically with `useMemo`:
  ```typescript
  const filteredList = useMemo(() => {
    return list.filter(item => item.name.includes(searchQuery));
  }, [list, searchQuery]);
  ```

### Form State Cleanliness
- Reset form fields on modal/dialog close.
- Ensure form data is validated locally before submitting server actions.

## 5. Design System & Styling Conventions

### Vibrant and Curated Color Palettes
- Adhere to the Indigo-Slate theme. Avoid generic, saturated colors like plain `#ff0000` (red) or `#00ff00` (green). Use curated Tailwind values like `indigo-600`, `emerald-500` (for success), `rose-500` (for errors), and HSL background colors for micro-cards.
- Ensure smooth transitions and hover micro-animations are added on interactive elements (`transition-all duration-200 hover:scale-[1.01] hover:bg-indigo-700`).

### Interactive Feedback & Typography
- Prevent button double-clicks during form submissions by adding a `disabled={isSubmitting}` property and rendering a loader spinner (`<Loader2 className="animate-spin" />`).
- Ensure custom web fonts (like Inter/Outfit) are used instead of default browser sans-serif fallbacks.

---

## 6. SEO, Accessibility & Clean Code

### SEO Best Practices
- Every main page component must export proper, descriptive metadata title and description:
  ```typescript
  export const metadata = {
    title: "Page Title - POS Admin",
    description: "Descriptive page summary",
  };
  ```
- Use a single, descriptive `<h1>` tag per page for correct semantic hierarchy.

### Accessibility (a11y)
- Every custom button component must declare `type="button"` unless it functions as the submit button (`type="submit"`) inside a form.
- Use semantic HTML tags (`<main>`, `<header>`, `<footer>`, `<section>`) instead of nested generic `<div>` blocks.

### Clean Code Practices & Import Rules
- **Mandatory `@/` Path Alias**: All internal module imports MUST use the `@/` path alias (e.g., `import { foo } from "@/lib/bar"`). Relative parent paths (`../`) are strictly prohibited.
- Clean up unused imports, dead functions, variables, and draft log outputs (`console.log`) before committing code.
- Write clear TypeScript interface declarations for all payloads, resources, and response structures.

### Git Operations Policy
- **DO NOT** execute `git commit` or `git push` commands under any circumstances. All git operations (committing and pushing) must be managed manually by the user/developer.
